文章的核心是：要让语音 AI 真正像“实时对话”，系统不能再按传统“一问一答”方式工作，而要让语音持续流动，把较慢的计算放到旁路异步完成。

```text
用户音频 ⇄ media frontend ⇄ voice model ⇄ 用户语音
                                  │
                    转写片段、时间、说话者线索
                                  ↓
                      application server（异步旁路）
                      ├─ 整理为离散消息与正式记录
                      ├─ 对接 UI、分析、安全等系统
                      └─ 委派复杂任务给 frontier model / 工具
                                  ↓
                    结果供 voice model 融入后续对话
```

我们的理解可以归纳为：

- **voice model 是实时对话的主体**：它全双工，能一边听一边说，不需要传统 turn detector 先判断“用户是否说完”。因此可以应对停顿、打断和重叠说话。
- **media frontend 是低延迟媒体通道**：只专注把音频帧稳定、快速地在客户端和 voice model 之间传送；不应承载慢业务逻辑。
- **application server 是产品编排层**：它虽处理“带时间和说话者信息的转写片段”，但职责并不只是文本处理；还包括消息整理、会话记录、UI/分析/安全支持、工具和模型委派等。
- **连续语音要被转换为离散消息**：聊天 UI、日志和安全系统仍需要“用户消息 / 助手消息”。服务器先维护可修订的暂定消息，等说话者归属可靠后再定稿，避免将“嗯”“好的”之类附和语错误记成独立回复。
- **实时性和确定性存在取舍**：太早定稿会造成消息碎裂、顺序不稳；太晚定稿又会让界面和下游功能滞后。因此系统同时保留“实时但可修改的视图”和“稳定的最终记录”。
- **delegation 是异步委派**：当需要深度推理、搜索或工具调用时，将任务交给更强的 frontier model；voice model 仍维持对话，待结果返回后自然融入回应。
- **委派链路也必须快**：路由、组装上下文、推理、工具调用都算进延迟预算。系统会预热前沿模型会话、预填充上下文和复用缓存。
- **有状态推理带来迁移问题**：长语音会话的上下文不断增长，模型实例也会按负载变化。为不中断通话，系统可预热替代实例、灌入当前上下文、并行推理，准备好后无缝切换。
- **启动阶段同样是关键路径**：用户点开语音后，媒体通道、协议握手和模型音频输入任何一步变慢，都会直接延迟“能开始说话”的时刻。

一句话概括：**让声音永不因后台思考而停顿，同时把连续、混杂的语音互动可靠地转换成产品所需的消息、记录和智能操作。**
