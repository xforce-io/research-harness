# Agentic Game Development as a Verifiable Trajectory Data Engine for Scaling World Models

> 靠爬更多视频堆算力缩放 world model 信号发虚 → 把游戏开发做成可执行世界规格，用引擎密检（碰撞/物理/可导航/可玩）叠开发者验收做 RL 奖励 → 空间生成也能像代码一样拿到可落地的后训练反馈。

## Essence

**问题**  
World model 常见缩放路径是“更多爬取视频 + 更多算力”，但空间生成侧缺少像代码编译器那样可执行、可复核的奖励；实践中多用 CLIP 等模糊代理分，难支撑可靠的 RL 后训练。

**做法**  
把游戏开发当作可验证轨迹数据引擎：场景由游戏引擎编码为可执行世界规格；引擎提供碰撞、物理、可导航性、有界可玩性等稠密检查；开发者对场景是否接受给出全局验证。据此提出 **RLHEV**（Reinforcement Learning with Human-Engine Verification），把引擎稠密信号与开发过程中的隐式人类接受反馈合成为后训练奖励。

**证据**  
所给正文仅为论点与范式陈述，**未给出**可引用的定量实验数字（无基准分、无相对提升倍数）。

**边界**  
这不是“再爬一批游戏视频当预训练语料”的方案；硬依赖是：目标表征能进游戏引擎执行校验，且存在开发者式验收闭环——不能把它读成通用视频 world model 的即插即用奖励层。

## Claims

- 仅靠爬取更多视频并增加算力来缩放 world model 是低效的；缩放还需要能提供有根基（grounded）奖励信号的递归数据引擎 [1: abstract]。
- 代码 agent 能成功做 RL 后训练，关键在于代码可执行，编译器与运行时能提供高质量奖励 [1: abstract]。
- 空间生成仍主要依赖 CLIP score 一类模糊代理信号；这类信号模糊且有偏，难以支撑 RL 后训练 [1: abstract]。
- 游戏开发能为空间 world model 提供缺失的奖励环境：引擎编码的场景是可执行世界规格，可高效检查碰撞、物理、可导航性与有界可玩性 [1: abstract]。
- 开发者通过对场景是否应被接受的判断，提供全局验证信号 [1: abstract]。
- 游戏开发还能为 RL 后训练提供真实世界长时程轨迹数据 [1: abstract]。
- RLHEV 将引擎稠密信号与开发过程中的隐式人类接受反馈结合，作为空间 world model 的后训练范式 [1: abstract]。

## Assumptions

- 游戏引擎检查（碰撞/物理/可导航/有界可玩）足以构成对“世界一致性”有用的稠密奖励，而不只是狭窄的工程约束 [1: abstract] `[low]`（由论证结构推出，文中未单独证明代表性）。
- 开发过程中的“接受/拒绝场景”可当作隐式、可用于 RL 的人类验证信号，且噪声与选择偏差可接受 [1: abstract]。
- 空间 world model / 场景生成的输出可以（或应被）映射为引擎可执行的场景规格，从而进入该奖励闭环 [1: abstract] `[low]`。
- 代码域“可执行 → 高质量 RL 奖励”的成功可类比迁移到空间生成域 [1: abstract]。

## Method

**直觉对比（奖励从哪来）**

| | 代码 agent | 常见空间生成 | 本文（游戏开发 / RLHEV） |
|---|---|---|---|
| 世界是否可执行 | 是（编译/运行） | 否或弱（多为静态生成物） | 是（游戏引擎场景规格） |
| 奖励形态 | 编译器/运行时等硬信号 | CLIP 等模糊代理 | 引擎稠密检查 + 人类验收 |
| 轨迹来源 | 写码—改码—跑测 | 多为短生成或代理打分 | 真实开发长时程轨迹 |

**流程（由论点还原的决策相关机制）**

1. **输入**：智能体/模型在游戏开发式流程中产出或修改场景（可执行世界规格），并留下长时程开发轨迹。
2. **引擎侧计算**：游戏引擎对场景做可自动复核的检查——碰撞、物理、可导航性、有界可玩性等，形成稠密、局部/过程级信号。
3. **人类侧信号**：开发者判断场景是否应被接受，形成全局、隐式的验收反馈（来自真实开发过程，而非另开一套标注）。
4. **输出 / 训练用途**：将引擎信号与人类验收合成为 RLHEV 后训练奖励，用于空间 world model 的 RL 后训练；同时把该开发过程本身当作可扩展的轨迹数据引擎。

（所给文本未展开奖励合成公式、智能体脚手架或具体引擎 API。）

## Weaknesses

- 论证停在范式对比（视频爬取 vs 可执行奖励；CLIP vs 引擎+人类），但未给出 RLHEV 的形式化奖励定义、训练目标或算法步骤，读者无法从正文复现训练回路 [1: abstract]。
- 将 CLIP 等代理分数一律归为“模糊且有偏、难支撑 RL”，未在所给文本中对照任何可执行或人类偏好基线的失败案例/定量反例，竞争命题偏断言化 [1: abstract]。
- “隐式人类接受反馈”的收集方式、延迟、偏好噪声与验收标准漂移未说明；若验收只发生在最终场景，可能稀疏到接近二元偏好，与“稠密引擎信号”如何加权仍是空缺 [1: abstract]。
- 引擎可检属性（碰撞/物理/导航/可玩）偏功能正确性，与感知真实感、语义合理性、开放世界多样性是否对齐未论证；存在优化成“引擎可过但视觉/语义差”的风险，文中未讨论 [1: abstract] `[low]`。
- 完全缺少实验与消融，缩放叙事（递归数据引擎）停留在动机层，无法评估相对“更多视频+算力”是否真更高效 [1: abstract]。

## Takeaway

- **可借用的方法要点**：把“可执行世界规格 + 自动环境检查 + 人类全局验收”拆成两类奖励通道，而不是只找一个更炫的代理分数。
- **需警惕/复核**：全文论点强、机制与实验在所给文本中几乎未落地；在看到正式奖励定义与对照实验前，不要把“游戏开发=world model 缩放引擎”当作已验证结论。
- **只记一句**：空间 world model 缺的不是更多模糊打分，而是像编译器一样能验世界的奖励环境——RLHEV 把游戏引擎检查和开发者验收接成这条回路。
